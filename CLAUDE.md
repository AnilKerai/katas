# CLAUDE.md

A collection of code katas (TDD training exercises) written in C# / .NET, grouped under a single
solution (`Katas.sln`).

## Structure

Each kata is its own project directory at the repo root, referenced from `Katas.sln`:

- `ABCGame/`
- `BowlingScoreCalculator/`
- `FizzBuzz/`
- `MagicSquare/`
- `PrintDiamond/`
- `Reordering/`
- `RomanNumerals/`
- `TextFormatter/`

`Katas.Testing/` is a shared support project (not a kata) referenced automatically by every kata.
`Katas.Testing.Tests/` holds the tests for its shared attributes (also not a kata); it gets the same test
stack as a kata and has no package references of its own.

A typical kata directory contains:

- `README.md` — the problem statement / kata brief
- `<Name>.cs` — the solution (production code)
- `<Name>Tests.cs` — the xUnit tests
- `<Name>.csproj` — the project file

FizzBuzz is also a console app: `XunitAutoGeneratedEntryPoint=false` stops xunit.v3 generating an entry
point, so its own `Program.cs` is the entry point, run with `dotnet run --project FizzBuzz`. `Program.cs`
hands a first argument that starts with a dash and isn't an integer to the xunit.v3 test runner; that is how
`dotnet test` runs the tests, since it starts the app with the runner's options (for example `--server`). Any
other first argument is a FizzBuzz argument, so `-5` still prints the usage message. `ProgramTests` calls the
entry point in-process (`Assembly.EntryPoint`) with the console redirected, which is how `Program.cs` is covered.

## Languages & test frameworks

- **Language / TFM:** C#, `net10.0` for every project, with `Nullable` and `ImplicitUsings` enabled. The
  TFM is set once in `Directory.Build.props`; project files must not set `TargetFramework`.
- **Test framework:** xUnit v3 (the `xunit.v3` package) on Microsoft Testing Platform (MTP). `dotnet test`
  uses MTP because `global.json` opts in. Each kata project is itself a test project — there is no separate
  src/test split; the solution code and its tests live side by side in the same project. xunit.v3 test
  projects are executables, so `Directory.Build.props` sets `OutputType` `Exe` for them.
- **Assertions:** Shouldly.
- **Test data / mocking:** AutoFixture (incl. `AutoFixture.Xunit3`) and NSubstitute.

Versions are pinned centrally via `Directory.Packages.props` (central package management is on, so
`<PackageReference>` entries omit versions).

## How test dependencies are wired

`Directory.Build.props` injects the common test stack into every kata project automatically (for any
project whose name is not `Katas.Testing`):

- The test packages above (`xunit.v3`, `Shouldly`, `AutoFixture`, `AutoFixture.AutoNSubstitute`,
  `AutoFixture.Idioms`, `AutoFixture.Xunit3`, `NSubstitute`, `Microsoft.Testing.Extensions.CodeCoverage`).
- `OutputType` `Exe`.
- Global `using`s: `Xunit`, `AutoFixture`, `AutoFixture.Xunit3`, `Shouldly`, `Katas.Testing`.
- A project reference to `Katas.Testing`.

`Katas.Testing/Attributes.cs` provides custom xUnit data attributes:
`AutoNSubstituteDataAttribute` and `InlineAutoNSubstituteDataAttribute`. `Katas.Testing.csproj` references
directly everything that file compiles against — `AutoFixture`, `AutoFixture.AutoNSubstitute`,
`AutoFixture.Xunit3`, `NSubstitute` and `xunit.v3.extensibility.core` — so it builds against the same
versions as the katas rather than the lowest versions AutoFixture's dependency ranges allow. It does not
reference `xunit.v3`: it is a library, and xunit.v3 would turn it into an MTP app.

This means a new kata project does **not** need to add its own package references, `Usings.cs`, or
test attributes — they come from the shared props/project.

## Build & test

Run from the repo root.

Build the whole solution:

```
dotnet build
```

Run all tests (every test project, `Katas.Testing.Tests` included):

```
dotnet test
```

Run the tests for a single kata:

```
dotnet test MagicSquare/MagicSquare.csproj
```

Run all tests with code coverage:

```
dotnet test --coverage --coverage-output-format cobertura --coverage-settings CodeCoverage.config --results-directory TestResults
```

This writes one `<guid>.cobertura.xml` per test project into `TestResults/` at the repo root, which git
ignores. `CodeCoverage.config` includes the test assembly in the report, because each kata keeps its code and
its tests in the same assembly and the coverage extension leaves the test assembly out by default.

### Coverage

`./scripts/coverage-check.sh` runs that command into a fresh `TestResults/coverage-check/` and prints lines and
branches per production file (any kata `.cs` file except `*Tests.cs`, `bin/`, `obj/` and the `Katas.Testing*`
projects). It exits 1 if a file is under 100% of lines or 95% of branches, 2 if coverage couldn't be measured.
It needs `python3` (standard library only). `scripts/coverage-exceptions.txt` lists code a test can't reach
(`path | reason`, or `path::Member | reason`); dead code is deleted, not listed.
Known gap: `MagicSquareCalculator.cs` is under target (1 line, 9 branches). Its `CalculateGrid` sum check only
fails for inputs the algorithm answers wrongly, so no passing test can cover it until the algorithm is fixed.

## Conventions & gotchas

- **TDD is the point.** The katas are training exercises; READMEs (e.g. `MagicSquare/README.md`)
  explicitly call out using TDD. Drive changes from tests.
- **One project per kata**, registered in `Katas.sln`. Adding a new kata means a new directory + a
  new `.csproj` added to the solution; the shared test setup applies automatically.
- Kata projects are not packable (`IsPackable=false`); they are test projects, and executables because
  xunit.v3 requires it.
- Don't add per-project package versions — central package management owns versions in
  `Directory.Packages.props`.
- Don't add per-project `Usings.cs`/`Attributes.cs`; `Directory.Build.props` removes them and global
  usings are provided.
- **`global.json` must stay.** It opts `dotnet test` into Microsoft Testing Platform; without it `dotnet test`
  fails on the .NET 10 SDK with "Testing with VSTest target is no longer supported". It holds only the test
  runner setting, no `sdk` pin. MTP projects don't need the VSTest-era packages (the test SDK, the VSTest
  runner adapter and coverlet's data collector); don't add them back.
- **The AutoFixture family is on `5.0.0-rc.1`**, the one allowed prerelease (`AutoFixture`,
  `AutoFixture.AutoNSubstitute`, `AutoFixture.Idioms`, `AutoFixture.Xunit3`). Move all four to `5.0.0`
  once it ships. Every other package is on its latest stable release.
- **Don't name the coverage settings `coverage*.xml`.** `.gitignore` ignores that pattern (and `coverage*.json`),
  which is why the file is `CodeCoverage.config`.
